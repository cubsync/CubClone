# 魅族 Flyme 应用分身（FlymeParallelSpace）原理分析

> 实测设备：魅族 18X（MEIZU_18X_CN），Flyme 10 移植版，Android 13（SDK 33），Magisk root。
> 分析对象：手机管家 `com.meizu.safe`（MzSecurity.apk v10.1.5）+ 系统设置 `com.android.settings`（Settings.apk）+ `framework.jar`。

## 结论先行

魅族的「应用分身」**不是**手机管家做的，管家首页只放了个入口卡片。真正的实现是：

- **底层**：AOSP 原生 **CLONE profile**（多用户克隆配置），固定 user id **999**，显示名 **FlymeParallelSpace**；
- **framework**：魅族在 `android.os.UserManager` 里加了几个隐藏方法（`createFlymeParallelSpace` / `startFlymeParallelSpace` / `getFlymeParallelSpaceStatus` 等）；
- **UI/管理**：系统设置 `com.android.settings` 里的 `com.meizu.settings.appclone` 包，反射调 framework 方法建空间，再 `installExistingPackageAsUser(pkg, 999)` 把应用装进分身。

跟我们 CubClone 用的是**同一套 `profile.CLONE`**，只是魅族把入口藏进了设置、把创建动作封装进了 framework。

## 一、实测证据（设备侧）

### 1. 分身空间 = user 999，CLONE profile

```
$ pm list users
UserInfo{0:机主:c13} running
UserInfo{999:FlymeParallelSpace:1010} running
```

```
$ dumpsys user
UserInfo{999:FlymeParallelSpace:1010} serialNo=10 isPrimary=false parentId=0
    Type: android.os.usertype.profile.CLONE      ← 关键：克隆配置文件
    Flags: 4112 (INITIALIZED|PROFILE)
    State: RUNNING_UNLOCKED
    Has profile owner: false
    Restrictions: none
```

`parentId=0` = 挂在机主下；`profile.CLONE` = AOSP 13 原生的「克隆配置文件」类型（不是 managed profile 工作资料，也不是 guest）。

### 2. 分身空间里装了哪些应用

```
$ pm list packages --user 999
com.tencent.mm                 ← 被分身的微信
com.tencent.soter.soterserver
com.android.phone / keychain / webview / gms ...
```

### 3. 运行态：同一 APK 两个 uid、进程完全隔离

```
$ ps -A | grep tencent.mm
u0_a212     9813  ...  com.tencent.mm            ← 主身份微信（appId 212）
u999_a212   9949  ...  com.tencent.mm            ← 分身微信（同 appId 212，不同 user）
u999_a212  15351  ...  com.tencent.mm:push       ← 分身微信的 push 进程
```

同一个应用（`com.tencent.mm`，appId 都是 212），在两个用户空间里各自起进程，uid 前缀 `u0_` vs `u999_`。这是 CLONE profile 的核心：**同一份 APK 被克隆到 user 999，拿到独立 uid、独立数据、独立进程**。

### 4. 数据与存储完全隔离

```
/data/user/999/            ← 分身空间独立数据目录（com.tencent.mm 等各一个）
/data/media/999/           ← 分身空间独立外置存储（DCIM/Pictures/Download... 全套）
```

### 5. 配置存 settings system

```
$ settings list system
mz_app_clone_enabled=1
mz_app_clone_enabled_pkgs=com.tencent.mm                    ← 已开分身的应用
mz_app_clone_ignore_pkgs=com.alipay.m.portal,com.pingan...   ← 禁分身黑名单（银行/支付/金融）
mz_app_clone_suggested_pkgs=com.tencent.mobileqq,...          ← 推荐可分身白名单
```

四个 `mz_app_clone_*` 键就是分身的全部配置源。黑名单里清一色银行/支付/券商，理由就是分身会复制安全环境、给风控和盗刷留口子。

## 二、代码链路（反编译证据）

### 1. 手机管家只是入口

`MzSecurity.apk` 首页 viewmodel `com.meizu.safe.mainpage.ui.viewmodel.c$h`：

```smali
:pswitch_b
    const-string v0, "com.meizu.settings.APP_CLONE_SETTINGS"
    invoke-virtual {v5, v0}, Landroid/content/Intent;->setAction(...)
```

管家点「应用分身」卡片 → 发一个 Intent action `com.meizu.settings.APP_CLONE_SETTINGS` → 跳转到**系统设置**。管家本体 dex 里没有任何 createProfile / installExisting / usertype 调用，纯转发。

### 2. 真正的实现在系统设置 `com.android.settings`

manifest 里注册了两个组件（`com.meizu.settings.appclone` 包，共 35 个类）：

```xml
<receiver android:name="com.meizu.settings.appclone.AppCloneReceiver"
          android:permission="flyme.permission.APPCLONE">
    <intent-filter>
        <action android:name="flyme.intent.action.APPCLONE_PACKAGE_REMOVED"/>
        <action android:name="flyme.intent.action.APPCLONE_PACKAGE_ADDED"/>
        <action android:name="android.intent.action.BOOT_COMPLETED"/>
    </intent-filter>
    <intent-filter>
        <action android:name="android.intent.action.PACKAGE_FULLY_REMOVED"/>
        <data android:scheme="package"/>
    </intent-filter>
</receiver>

<activity android:name="com.meizu.settings.MzSettingsActivity$AppCloneSettingsActivity">
    <intent-filter>
        <action android:name="com.meizu.settings.APP_CLONE_SETTINGS"/>
    </intent-filter>
    <meta-data android:name="com.android.settings.FRAGMENT_CLASS"
               android:value="com.meizu.settings.appclone.AppCloneSettings"/>
</activity>
```

核心类分工：

| 类 | 职责 |
| --- | --- |
| `AppCloneSettings` | 分身设置页 Fragment（UI） |
| `AppCloneState` | 状态管理，读写 `mz_app_clone_*`（走 ContentProvider） |
| `AppCloneUpdateHelper$EnableTask` | **核心动作**：建空间 + 装应用 |
| `AppCloneIntentService` | 后台执行安装/卸载 |
| `AppCloneReceiver` | 监听应用安装/卸载/开机广播 |
| `AppClonePkgsFetcher` | 拉取可分身应用列表 |

### 3. 关键动作：`AppCloneUpdateHelper$EnableTask.doInBackground`

反编译 smali 还原成 Java 伪代码：

```java
UserManager um = (UserManager) context.getSystemService(UserManager.class);
IReflectClass rc = ReflectUtils.from(um);

// 1. 查平行空间状态（-1 = 未创建）
int status = (Integer) rc.method("getFlymeParallelSpaceStatus").invoke(um);

if (status == -1) {
    // 2. 空间不存在 → 创建 CLONE profile
    boolean ok = (Boolean) rc.method("createFlymeParallelSpace").invoke(um);
    if (!ok) { logW("createFlymeParallelSpace failed"); return false; }

    // 3. 启动该用户（等价 am start-user 999）
    ok = (Boolean) rc.method("startFlymeParallelSpace").invoke(um);
    if (!ok) { logW("startFlymeParallelSpace failed"); return false; }
}

// 4. 把目标应用克隆安装进分身空间（0x3E7 = 999）
int res = pm.installExistingPackageAsUser(mPkg, 0x3E7);   // 等价 pm install-existing --user 999
```

四个动作，和我们 CubClone 的实现**完全同构**：建 profile → 启动用户 → `install-existing` 装应用。

### 4. framework.jar 的 UserManager 定制

framework.jar 的 `classes3.dex` 里存在这些方法（`android.os.UserManager` 被魅族加了扩展）：

```
FlymeParallelSpace
createFlymeParallelSpace
startFlymeParallelSpace
getFlymeParallelSpaceStatus
getFlymeParallelSpaceUserIds
```

同时 framework 里确认：

```
android.os.usertype.profile.CLONE     ← 使用的 profile 类型常量
createProfileForUser                  ← 标准 AOSP 建 profile 接口（出现 6 次）
```

即：魅族的 `createFlymeParallelSpace()` 内部就是调 `createProfileForUser(name="FlymeParallelSpace", type="android.os.usertype.profile.CLONE", ...)`，然后 `start-user 999`。

> 注意：`framework-res.apk` 里的 `config_user_types.xml` 是空的 `<user-types />`，说明魅族没走资源表定义 CLONE，而是 framework 代码里硬编码了 CLONE 类型（AOSP 默认就有这个类型，魅族只是包一层方便方法）。

## 三、完整流程图

```
[手机管家首页卡片]
        │  Intent action "com.meizu.settings.APP_CLONE_SETTINGS"
        ▼
[系统设置 AppCloneSettingsActivity]
        │  Fragment: com.meizu.settings.appclone.AppCloneSettings
        ▼
[AppCloneUpdateHelper$EnableTask]  (用户点某应用的「分身」开关)
        │
        ├─ 反射 UserManager.getFlymeParallelSpaceStatus()  ──→  已存在? ── 否 ──┐
        │                                                         是          │
        │                                                        ┌───────────┘
        │  createFlymeParallelSpace()  ─→ createProfileForUser(CLONE)  → user 999
        │  startFlymeParallelSpace()   ─→ am start-user 999
        │
        └─ PackageManager.installExistingPackageAsUser(pkg, 999)
                                        │
                                        ▼
                     user 999 内独立安装该应用
                     (独立 uid u999_a212 / 独立 /data/user/999 / 独立 /data/media/999)
```

配置全程读写 `settings system` 的 `mz_app_clone_enabled_pkgs` 等四个键；`AppCloneReceiver` 监听应用安装/卸载/开机事件，自动同步分身空间。

## 四、对 CubClone 的启示

1. **原理同源**：魅族和我们都是 `profile.CLONE` + `install-existing --user`。方向对，不用换。
2. **魅族把入口放设置、动作封装进 framework**（`UserManager` 反射方法），好处是普通应用拿不到 `MANAGE_USERS` 权限也能建空间（framework 方法以系统身份执行）；坏处是要改 ROM。我们走 Shizuku(shell) 是第三方应用的现实解，等价能力。
3. **黑名单机制值得抄**：`mz_app_clone_ignore_pkgs` 把银行/支付/券商整批禁分身。这不是技术限制，是产品决策——规避盗刷/风控/封号投诉。我们做白名单/黑名单时可以直接参考这份清单逻辑。
4. **数量限制**：魅族实测单空间（1 个 CLONE profile，user 999 固定）。和红米 `mMaxAllowedPerParent=1` 一致，`profile.CLONE` 默认每父用户上限 1。
5. **相册互通问题**：魅族分身空间 `/data/media/999` 是独立目录（DCIM/Pictures 各一套），**不是** bind mount 共享。而 CubClone 记忆里写「相册/MediaStore 与父用户共享」——这点要复核：CLONE profile 的 MediaStore 互通是 AOSP 的 cross-profile 挂载机制，不是文件系统层共享。魅族是否启用了 cross-profile 媒体共享，需再验一次（看 media provider 对 999 的挂载），别把「默认互通」当定论。
